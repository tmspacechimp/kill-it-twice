# G1: Resume after the replicator crashes

G1 checks that a sudden replicator crash does not lose events, that processing
resumes from saved progress, and that the consumer detects a replayed event.

## How it works

On its first startup, the replicator saves the highest source event ID as its
**initial-load boundary**. One reader processes rows through that boundary;
another processes newer rows concurrently. Restarts keep the original boundary.

The replicator stores the boundary and both readers' progress in **SQLite on a
persistent Docker volume**. Each cursor advances only after OpenSearch accepts
the write and RabbitMQ confirms publication. A replacement container resumes
each reader after its saved cursor.

A crash after publication but before checkpointing causes an event to be
processed again.

**OpenSearch handles replays safely.** Each shipment uses its shipment ID as the
document ID and its source version as OpenSearch's external version. OpenSearch
replaces the document only when the incoming version is higher. A replay with
the same version, or an older event arriving later, gets a version conflict.
The replicator recognizes that conflict, skips the index write, and still
publishes the event to RabbitMQ. This prevents duplicate documents and stops
old events from overwriting newer shipment state. It relies on immutable source
events and this pipeline owning the shipment index.

The consumer stores processed event IDs in **its own SQLite
database and persistent volume**. This lets it detect duplicates even after
the consumer itself is killed and restarted, provided the volume survives.
G1 restarts only the replicator; it does not test a consumer crash.

## How the crash is simulated

The verification run selects `G1PublisherService`, a child of the normal
publisher, through the `G1_CRASH_EVENT_ID` environment variable. For that event,
the child calls the normal publish method, waits for RabbitMQ's confirmation,
then sends itself `SIGKILL`: immediate termination without cleanup.

**The crash is after RabbitMQ's acknowledgement, but before the replicator saves
its checkpoint.** This gives us a known published event that must be replayed.
The test clears the variable before restarting, selecting the normal publisher.

## How it is tested

The test creates isolated Docker services and requires all of the following:

1. Seed the initial dataset, then append nine incremental events while the
   initial reader is still running.
2. Crash at `G1_CRASH_EVENT_ID`. Require exit code 137, an initial cursor exactly
   one less than that ID, an unfinished initial load, and all nine incremental
   events checkpointed.
3. Before restart, require the consumer's normal log for the crash event with
   its full matching source payload and no duplicate log for that ID.
4. Recreate the replicator with its saved volume. Require the first resumed
   initial event to be the crash event and an explicit consumer duplicate log
   for that same ID.
5. After initial loading finishes, append nine more events. Require exactly one
   normal consumer log with the correct payload for **every source event**, and
   compare **every shipment's highest source version** with its OpenSearch document.

`G1 PASS` appears only after these checks, a successful replicator exit, and
cleanup. Counts alone cannot pass: the comparisons reject missing IDs, repeated
normal processing, incorrect payloads, and incorrect shipment state.

The crash event reached the consumer before restart but was absent from saved
progress. Its duplicate log after restart proves that replay and duplicate
detection actually occurred.

## Configuration and running

- `SEED_SHIPMENTS=4000` in `.env` creates **10,000 initial events**.
- `G1_CRASH_EVENT_ID=2048` in `.env.verify` selects the crash event.
- `G1_WAIT_TIMEOUT_MS=600000` in `.env.verify` allows ten minutes per verification stage.

Run `make verify` from the repository root.

## Concerns

**Database work per event.** The replicator commits a checkpoint for each
completed event; the consumer attempts a receipt insert for every delivery.
The consumer avoids a preliminary lookup with
`INSERT ... ON CONFLICT DO NOTHING RETURNING event_id`: the unique key checks
for duplicates. A returned ID means new; no returned row means already recorded.
This saves a separate read, not the cost of persistence or checkpoint writes.

We cannot quantify the performance impact without comparable versions with and
without these writes and suitable metrics. Those measurements are not available
for this change. If checkpoint commits become a bottleneck, batching could
reduce them at the cost of replaying more events after a crash. Consumer
duplicate detection would still be required.

**Scope.** G1 covers a replicator process crash while its checkpoint volume and
destination services survive, under the single serial source-writer assumption.
It does not establish recovery from broker or disk loss, or exactly-once console
logging. A consumer crash between committing its receipt and logging could omit
the normal log even though the receipt survives.
