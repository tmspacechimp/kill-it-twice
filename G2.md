# G2: Harmless replay across repeated replicator crashes

This case checks that repeated replicator process crashes lose no source events
and that replay leaves the correct shipment state and is detected by the consumer.
It covers a finite schedule of initial and incremental crashes toward G2; it
does not complete the entire G2 epic.

## How recovery works

The recovery mechanism is the same as [G1](G1.md). SQLite on the replicator's
persistent volume stores the original initial-load boundary and both readers'
cursors. Each cursor advances only after both OpenSearch writes succeed and
RabbitMQ confirms publication. Recreating the replicator retains that boundary
and resumes each reader after its saved cursor.

Shipment ID identifies the current-state document, and external source versions
prevent equal or older events from replacing newer state. Replays still append
full payloads to `shipment-records`, preserving delivery evidence. The consumer's
own persistent SQLite receipts detect repeated event IDs and suppress repeated
normal handling. History duplicates and duplicate notices are expected.

## How the crashes are simulated

`make verify-g2` installs one `G2_CRASH_EVENT_IDS` target per replicator run.
The shared `CrashInjectingPublisherService` waits for the target's broker
confirmation, then sends SIGKILL before its reader checkpoints. Each run must
exit with code 137 and leave that reader's cursor at target minus one.

The default schedule `[2048,2048,12048]` kills twice at the same initial event,
then once at an incremental event above the default 10,000-row boundary. The
repeated initial target must replay immediately after restart. The incremental
crash can interrupt initial work too; checks allow that reader's independent
progress while preserving both saved cursors.

Traffic for the first incremental target is written after its hook is installed,
so an earlier run cannot pass that target. Another batch is written while stopped
before the final restart. This supplies activity for the restarted incremental
reader and preserves the startup-wait and idle-stop rules in [SPEC.md](SPEC.md).

## What the scenario must prove

1. Each scheduled run loads the preceding checkpoint, retains the original
   boundary, and crashes at the requested event with the expected cursor.
2. The consumer receives the crash event with its source payload; preceding
   scheduled replays are detected before moving to the next target.
3. The final restart restores both cursors without injection, finishes initial
   and supplied incremental work, and exits successfully.
4. Every source event has exactly one normal consumer log with the full matching
   payload. Each scheduled replay has a duplicate notice.
5. Every shipment matches its highest source version and payload in OpenSearch,
   with exactly the expected number of shipment documents.
6. Full history scanning finds every source payload. A target scheduled for
   two crashes has at least three distinct history deliveries; a target scheduled
   once has at least two. Extra replays from the concurrent reader are allowed.

Missing IDs, corrupt payloads, repeated normal handling, stale shipment state,
missing replay evidence, or failed cleanup produce FAIL. `G2 PASS` requires all
checks and cleanup to succeed. Counts alone do not satisfy these comparisons.

## Recorded evidence

A scaled Docker run used 1,001 seed shipments (2,503 initial events), 600 events
per incremental batch, and schedule `[2048,2048,2700]`. All three kills exited
137. At the incremental kill, the initial cursor was 2,297 with initial loading
unfinished, while the incremental cursor was 2,699. This records an actual
incremental crash alongside initial work.

The final run resumed initial work at 2,298 and completed both cursors. Checks
passed for 3,703 source events, 1,401 latest shipment documents, three consumer
duplicate notices, and 3,706 history documents. The default 22,000-event fixture
was not rerun for this change. See the [validation history](docs/validation-history.md)
for commands and run IDs, and the [G2 case guide](docs/g2-verification.md) for
configuration and retained evidence fields.

## Assumptions and limits

This proof assumes one serial append-only source writer, one replicator per
checkpoint volume, one surviving consumer per receipt volume, and intact source,
destinations, and volumes. Only the replicator is killed and recreated.

It demonstrates at-least-once processing and harmless replay for the tested
schedule. It does not establish consumer-crash recovery, broker or disk-loss
recovery, exactly-once delivery or logging, or every possible failure schedule.
The two index writes, publication, and checkpoint remain separate operations.
